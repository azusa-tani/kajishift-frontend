# KAJISHIFT リリース判定用 テストケース一覧

## 1. 文書の目的

- 本書は、KAJISHIFT のリリース判定に使用するテストケース一覧である。
- `RELEASE_TEST_PERSPECTIVES.md` の観点を、実行可能な操作手順と期待結果に落とし込む。
- 実施結果は `docs/RELEASE_TEST_RESULTS.md` に記録する前提とする。
- 一覧表の「判定」列が「未実施」のままであっても、既に `docs/RELEASE_TEST_RESULTS.md` に記録されたケースはそちらを正とする（例: 2026-05-12 時点で TC-E-001・TC-E-004 は OK、TC-E-002・TC-E-003・TC-N-001・TC-SEC-001 は保留）。
- 不具合が出た場合は `docs/RELEASE_DEFECT_LIST.md` に記録する前提とする。

## 2. 前提

- 対象は `kajishift-frontend` および `kajishift-backend`。
- 本番想定は、フロントは Vercel、バックエンドは Railway。
- 現時点で本フロントリポジトリには自動テストコード・CI 上のテスト実行設定がないため、まずは手動テストを主とする。
- 「自動化候補」は、現時点で自動テストが存在するという意味ではなく、将来的に Playwright や API テストとして自動化しやすい項目を示す。
- 決済は外部決済サービス連携の有無が要確認であり、現時点では「外部PSP連携あり/なし」の両方を考慮する。
- 本書に記載するメールアドレス・パスワードは例であり、実際のテストではステージングまたは本番確認用に払い出されたテストアカウントを使用する。

## 3. テスト実施方針

- 重要度「高」かつリリース必須「Yes」の項目を優先して実施する。
- 未実施または NG がある場合は、原則リリース不可またはリリース判定会議で承認が必要。
- 重要度「中」はリリース前実施を推奨し、未実施の場合は残課題として管理する。
- 重要度「低」はリリース後対応も可とする。
- 画面操作で確認するもの、API クライアントで確認するもの、インフラ設定で確認するものを分けて実施する。
- バックエンド・インフラ・外部サービス依存の項目は、備考に依存先を明記する。
- 判定は「未実施」で開始し、証跡は初期値「－」とする。

## 4. 判定基準

| 判定 | 意味 |
|---|---|
| OK | 期待結果どおり |
| NG | 期待結果と異なる |
| 保留 | 環境・仕様・データ不足で判断できない |
| 対象外 | 今回リリース範囲外 |

以下はリリース不可候補として扱う。

- ログインできない
- 権限不一致なのに本来アクセスできない画面またはAPIにアクセスできる
- 予約作成・変更・キャンセルが正常にできない
- ワーカーの承諾・拒否・完了が正常にできない
- 決済で二重決済、決済失敗時の不整合、領収書出力不可が発生する
- 顧客・ワーカー・予約・決済データが誤って登録・更新・削除される
- 管理者の主要機能が正常にできない
- 個人情報、JWT、認証情報、管理画面情報が不適切に露出する
- 本番API、Socket、CORS、SSLなどの設定が誤っている
- 本番リリース後に切り戻しできない
