# KAJISHIFT リリース判定用 切り戻し手順書

## 1. 文書の目的

- 本書は、KAJISHIFTの本番リリース後に重大な問題が発生した場合の切り戻し手順を定義する。
- 切り戻しの対象は、フロントエンド、バックエンド、DB、環境変数、外部連携設定とする。
- 切り戻し可否はリリース判定の重要条件である。
- 本書は `docs/RELEASE_TEST_CASES.md`、`docs/RELEASE_TEST_RESULTS.md`、`docs/RELEASE_DEFECT_LIST.md`、`docs/RELEASE_CRITERIA.md` と併用する。

## 2. 前提

- フロントエンドは Vercel で配信される想定。
- バックエンドは Railway で稼働する想定。
- フロントエンドは静的サイトとしてデプロイされる想定（`vercel.json`）。
- バックエンドは別リポジトリとして管理される想定（`kajishift-backend`）。
- DBはバックエンド側で管理される想定（PostgreSQL + Prisma）。
- DBマイグレーションの有無により切り戻し手順が変わる。
- 本書作成時点で不明な内容は「要確認」と明記する。
- 実際の本番環境の操作権限、管理画面、バックアップ方式は運用担当に確認する。

## 3. 切り戻し対象

| 対象 | 内容 | 切り戻し方法 | 備考 |
|---|---|---|---|
| フロントエンド | Vercel上の静的サイト | 前回デプロイへの戻し | 要確認 |
| バックエンド | Railway上のAPIサーバー | 前回デプロイ/コミットへの戻し | 要確認 |
| DB | 本番DB | バックアップ復元またはフォワード修復 | DB変更有無で判断 |
| 環境変数 | API URL、CORS、JWT、SMTP等 | 変更前値へ戻す | 事前控え必須 |
| Socket | Socketサーバー設定 | バックエンドと同時確認 | 要確認 |
| 外部連携 | SMTP、決済、ファイル保存等 | 変更前設定へ戻す | 要確認 |

## 4. 切り戻し判断基準

| 条件 | 判断 |
|---|---|
| 全ロールでログインできない | 即時切り戻し候補 |
| 予約作成・変更・キャンセルができない | 即時切り戻し候補 |
| ワーカーの承諾・拒否・完了ができない | 即時切り戻し候補 |
| 決済で二重決済・不整合が発生 | 即時切り戻し候補 |
| 管理者が主要機能を利用できない | 切り戻し候補 |
| 権限不備により越権アクセスできる | 即時切り戻し候補 |
| 個人情報・JWT・認証情報が露出 | 即時切り戻し候補 |
| 本番APIまたはSocketへ接続できない | 切り戻し候補 |
| 軽微な表示崩れのみ | 原則切り戻し不要、修正リリース検討 |
| 回避策があり業務継続可能 | 判定会議で判断 |

## 7. フロントエンドの切り戻し手順

Vercelを前提にした一般手順（実環境操作は要確認）。

1. Vercelの対象プロジェクトを開く。  
   - 対象: `kajishift-frontend`（要確認）
2. Deploymentsから直前の安定版デプロイを確認する。  
   - 安定版のデプロイID/時刻/コミットを記録する。
3. 安定版をProductionへPromoteまたはRedeployする。  
   - 操作名称や実行権限はVercel画面仕様に依存するため要確認。
4. `js/config.js` の `API_BASE_URL` / `SOCKET_SERVER_URL` が意図した値か確認する。  
   - 現行想定値: `https://kajishift-backend-production.up.railway.app/api` と `https://kajishift-backend-production.up.railway.app`。
5. 主要画面へアクセスして表示を確認する。  
   - `index.html`、`customer/login.html`、`worker/login.html`、`admin/login.html`。
6. ブラウザキャッシュ・Service Workerの影響を確認する。  
   - ハードリロード、別ブラウザ/シークレットモードでも確認する。

## 8. バックエンドの切り戻し手順

Railwayを前提にした一般手順（実環境操作は要確認）。

1. Railwayの対象サービスを開く。
2. 直前の安定版デプロイまたはコミットを確認する。
3. 安定版へ戻す。  
   - Railwayの具体UI操作、またはコミット指定デプロイ方法は要確認。
4. 環境変数が切り戻し後のバージョンと整合しているか確認する。  
   - `DATABASE_URL`、`JWT_SECRET`、`CORS_ORIGIN`、SMTP関連、その他運用変数。
5. APIヘルスチェックを実行する。  
   - 例: `GET /api/health`。
6. 認証・予約・決済・管理APIの代表疎通を確認する。  
   - 例: `/api/auth/login`、`/api/bookings`、`/api/payments`、`/api/admin/*`。
7. Socket接続を確認する。  
   - 接続可否と通知/メッセージイベントの受信可否を確認する。
8. ログに重大エラーがないことを確認する。  
   - Railwayログ上の5xx、DB接続失敗、認証失敗連発等を確認する。

## 9. DB変更がない場合の切り戻し手順

- DBスキーマ変更がない場合、原則としてアプリケーションの前バージョン戻しを優先する。
- フロント・バックを安定版に戻す。
- API疎通確認を行う。
- 既存データに不整合がないか確認する。
- 予約・決済・ログイン・管理機能の代表確認を行う。

補足:

- このケースではDB復元を行わず、アプリケーション切り戻しで収束を図る。
- ただし、リリース後にデータ修正バッチ等を実行している場合は、個別に影響評価する（要確認）。

## 10. DB変更がある場合の切り戻し手順

- DBマイグレーションがある場合は、単純なアプリケーション切り戻しだけでは不整合が起きる可能性がある。
- リリース前バックアップから復元するか、フォワード修復するかを判断する。
- 本番DBの復元は影響が大きいため、DB担当・リリース責任者の承認を必須とする。
- データ消失や予約・決済データの巻き戻りが起きる可能性を確認する。
- 予約・決済・ユーザー更新など、リリース後に発生したデータの扱いを決める。
- Prisma等のマイグレーション履歴を確認する。  
  - 例: `prisma/migrations`、`prisma migrate deploy` 実行履歴。
- DB復元後、アプリケーションとスキーマの整合を確認する。

| 判断項目 | バックアップ復元 | フォワード修復 |
|---|---|---|
| データ巻き戻り | 発生する可能性あり | 原則避けられる |
| 実施難易度 | 中〜高 | 高 |
| 所要時間 | 要確認 | 要確認 |
| 向いているケース | 重大なスキーマ破損 | データ巻き戻しを避けたい場合 |
| 承認 | 必須 | 必須 |

## 11. 環境変数・外部連携設定の切り戻し

| 設定項目 | 内容 | 切り戻し確認 | 備考 |
|---|---|---|---|
| API_BASE_URL | フロントから接続するAPI URL | 変更前値に戻っているか | `js/config.js` |
| SOCKET_SERVER_URL | Socket接続先 | 変更前値に戻っているか | `js/config.js` |
| CORS_ORIGIN | 許可オリジン | フロントURLが許可されているか | Railway |
| JWT_SECRET | JWT検証キー | 変更有無を確認 | 原則変更しない |
| DATABASE_URL | DB接続先 | 本番DBを指しているか | 要確認 |
| SMTP設定 | メール送信 | 変更前値に戻っているか | 要確認 |
| 決済設定 | PSP連携がある場合 | テスト/本番キーの取り違えがないか | 要確認 |
| ファイル保存設定 | 添付ファイル保存先 | 変更前値に戻っているか | 要確認 |

## 15. リリース判定への影響

- 本書が未作成、または切り戻し手順が未確認の場合、リリース判定では保留またはNo-Go候補とする。
- `docs/RELEASE_TEST_CASES.md` の `TC-O-002`、`TC-O-003` は本書の内容を確認対象とする。
- DB変更があるリリースでは、DB復旧方針が未確定のままリリースしない。
- 切り戻し後の動作確認が実施できない場合、切り戻し成功とはみなさない。
